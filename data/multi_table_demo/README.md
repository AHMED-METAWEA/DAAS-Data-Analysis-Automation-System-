# Bloom & Bean — multi-table test dataset

The same fictional coffee-roastery business as `../bloom_and_bean_sales.csv`,
but normalized into three related tables the way a real company's data
actually looks, instead of one flat export. Generated by
[`generate_multi_table_business_data.py`](../../Generate_Data/generate_multi_table_business_data.py)
(deterministic, seed = 11).

## Files (upload all 3 together to Data Cleaning)

| File | Rows | Role |
|---|---|---|
| `customers.csv` | ~353 | dimension |
| `products.csv` | 20 | dimension |
| `orders.csv` | ~5,190 | fact — references both dimensions |

`clean/` holds the clean reference versions of all three (for diffing).

## Schema

```
customers (customer_id PK) ──┐
                              ├──< orders (customer_id FK, product_id FK)
products (product_id PK) ────┘
```

- **customers**: `customer_id, customer_name, email, region, country, signup_date`
- **products**: `product_id, product_name, category, unit_cost, base_price`
- **orders**: `order_id, order_date, ship_date, customer_id, product_id, quantity, unit_price, discount_pct, total_price, cost, profit, marketing_channel, payment_method`

## What each stage should find

- **Schema Discovery** — `orders.customer_id → customers.customer_id` and
  `orders.product_id → products.product_id` should both land in the
  **auto-approved** bucket (exact name match, high PK uniqueness, high FK
  coverage).
- **Cleaning** — each table has its own dirtiness: missing values/placeholders
  (`Unknown`, `N/A`, `-`, `?`, `TBD`, `call for price`), type mismatches,
  price/quantity outliers, duplicate rows, malformed dates, inconsistent
  casing.
- **Reconciliation** — both join keys have a small amount of deliberate
  whitespace/casing drift (e.g. `"SKU-1019"` vs `"sku-1019"`, a stray
  trailing space on some `customer_id`s). Small enough that Schema Discovery
  still detects the relationship, real enough that independent per-table
  cleaning could plausibly make it worse — watch the before/after orphan
  rate on the Data Cleaning page after cleaning all three tables.
- **Storage/views** — `orders` is the natural fact table (it's the only one
  referencing anything), so the semantic view joins in both `customers` and
  `products` in a single hop — every downstream page should see customer
  and product attributes alongside the transaction data.
- **Forecasting / Marketing / Churn** — same signal as the flat version: an
  upward trend, weekly + Q4 seasonality, a Black-Friday spike, a March
  supply-outage dip, and a full RFM archetype spread (Champions, At Risk,
  Loyal, Hibernating, Lost, …).
